# GAPS v1.0.0 Design

## Context

GAPS v0.1 is a structured-documentation format for governed processes. The current schema (`gaps/schema/ga-process.schema.json`) requires section presence and enforces enum values for autonomy tier / risk tier / authority plane / gate type, but every other load-bearing field is free text. The validator does not enforce cross-references (`approvalRole` is not checked against `roles` keys; gate ids are not checked for uniqueness; skill paths are not resolved). The generator (`scripts/generate-gaps-skill-package.py`) emits skill skeletons with hard-coded section headers ("Input Quality Gate", "Rules", "Stop Conditions") because the spec does not contain enough structured information to derive skill content.

Comparing the four reference specs (`gadd`, `compliance-review`, `incident-response`, `procurement-approval`) confirms the consequence: ~99% of vocabulary in `authority.allowed`/`authority.prohibited` is unique to each spec. Two authors — human or LLM — writing specs for the same process produce structurally incomparable YAML. A generator can only embed that prose verbatim.

GAPS v1.0.0 fixes this with a single goal: **an LLM (or a careful human) can author a v1 spec from a real process, and a generator can emit usable governed-autonomy skills from that spec without humans inventing skill content at adoption time**. The round-trip property — spec → skill package → recovered spec — is the design target. Authoring rigor falls out of round-trippability.

The design adopts OSCAL structurally for evidence and control mappings, adopts CMMN's case/stage/milestone and DMN's decision-table concepts conceptually (rendered in GAPS-native YAML), and adds three new things v0.1 lacks: a controlled action catalog, a typed evidence model, and an executable state-and-gate model per lane.

## Substrate Recommendation

**OSCAL: structural adoption.** The `evidence` and `control_mappings` blocks become subsets of OSCAL component-definition and assessment-results shapes. Control catalogs (NIST AI RMF, ISO/IEC 42001 Annex A, EU AI Act key articles) ship as OSCAL catalog files in `gaps/catalogs/controls/`. A spec's `control_mappings` block references control UUIDs from those catalogs. Evidence items use OSCAL evidence schema with `uuid`, `props`, `links`. This gives real interop: a v1 GAPS spec's `controls_assessment_plan` is a valid (subset) OSCAL assessment-plan document.

**CMMN: conceptual adoption.** Stages (≈ lanes), milestones (≈ approved boundaries), case file items (≈ typed evidence inputs/outputs), sentries (≈ entry/exit conditions). Rendered as GAPS-native YAML with field names that read naturally for governed-autonomy work (`lanes`, `gates`, `evidence_inputs`, `entry_conditions`).

**DMN: conceptual adoption.** Each gate is a decision table: typed inputs from case file items, decision rules, conclusion = `approve` | `escalate` | `reject` with downstream effect (transition to state). FEEL-style expressions kept simple — string equality, numeric comparison, `defined`/`undefined`, boolean combinators. No imported FEEL runtime; expressions evaluable in Python.

**GAPS-native overlay.** `authority_planes`, `autonomy_tiers`, `risk_tiers`, `governed_autonomy_risk_patterns`, `drift_and_freshness`, `projection_policy` remain GAPS-native — they have no good home in OSCAL/CMMN/DMN.

## Architecture Overview

Six coupled layers. The design doc covers all six; each layer becomes its own implementation plan (via the writing-plans skill) after this design is approved.

```
┌─────────────────────────────────────────────────────────────┐
│ Layer 6: Round-trip + reverse-lift tooling                  │
├─────────────────────────────────────────────────────────────┤
│ Layer 5: Migration (v0.1 → v1) + reference spec ports       │
├─────────────────────────────────────────────────────────────┤
│ Layer 4: Generator v1 — derives skill content from spec     │
├─────────────────────────────────────────────────────────────┤
│ Layer 3: Validator v1 — schema + semantic + integrity       │
├─────────────────────────────────────────────────────────────┤
│ Layer 2: Catalogs (actions, evidence kinds, risk, controls) │
├─────────────────────────────────────────────────────────────┤
│ Layer 1: Formal model — the v1 spec format itself           │
└─────────────────────────────────────────────────────────────┘
```

The vertical order matches the dependency order. Layer 1 + Layer 2 unblock everything else.

## Layer 1: Formal Model

A v1 spec is one YAML document. Top-level shape:

```yaml
gapsVersion: "1.0.0"
specStatus: published | draft | deprecated
conformanceLevel: descriptive | machine-validatable | generative

process:
  id: <slug>
  name: <string>
  purpose: <string>
  scope:
    includes: [<string>, ...]
    excludes: [<string>, ...]

substrate:
  oscalControlCatalogs:
    - gaps/catalogs/controls/nist-ai-rmf.json
    - gaps/catalogs/controls/iso-42001-annex-a.json
  oscalProfile: gaps/catalogs/controls/profiles/<process-id>-profile.json  # optional
  actionCatalog: gaps/catalogs/actions/v1.yml
  evidenceCatalog: gaps/catalogs/evidence-kinds/v1.yml
  riskPatternCatalog: gaps/catalogs/risk-patterns/v1.yml

roles:
  - id: <role-id>
    label: <string>
    accountabilityScope: <string>
    decisionRights: [<action-ref>, ...]   # references action catalog
    canApprove: [<gate-id>, ...]          # cross-ref enforced

evidenceModel:
  caseFileItems:
    - id: <evidence-id>
      kind: <evidence-kind-ref>           # references evidence catalog
      label: <string>
      shape:                              # typed shape, OSCAL props-compatible
        required: [<field>, ...]
        optional: [<field>, ...]
      producer: <role-ref> | lane:<lane-id> | external
      consumer: [<role-ref|lane-ref>, ...]
      retentionPolicy: <string>           # OSCAL prop

lanes:
  - id: <lane-id>
    label: <string>
    purpose: <string>
    authority:
      plane: data_plane | control_plane
      autonomyTier: <enum>
      riskTier: <enum>
      allowedActions: [<action-ref>, ...]      # action catalog
      prohibitedActions: [<action-ref>, ...]   # action catalog
    stateModel:
      states:
        - id: <state-id>
          label: <string>
          isInitial: bool
          isTerminal: bool
      transitions:
        - id: <transition-id>
          from: <state-id>
          to: <state-id>
          guard:                          # DMN-style decision
            inputs: [<case-file-item-ref>, ...]
            rules:
              - when: <feel-subset-expression>
                then: allow | block
            else: block
          gate: <gate-id>                 # optional; transition gated by a gate
    evidenceInputs: [<case-file-item-ref>, ...]
    evidenceOutputs: [<case-file-item-ref>, ...]
    autonomousResponsibilities: [<action-ref>, ...]
    skills: [<skill-id>, ...]             # implementation map binding

gates:
  - id: <gate-id>
    label: <string>
    gateType: validating | blocking | escalating | advisory
    approvalRole: <role-ref>              # cross-ref enforced
    decision:                             # DMN-style table
      inputs: [<case-file-item-ref>, ...]
      rules:
        - when: <expr>
          then: approve | escalate | reject
          effect:
            transitionTo: <state-id>      # optional
            recordEvidence: [<evidence-id>, ...]
      else: escalate
    approvalCondition: <string>           # human-readable, derived from rules
    escalationCondition: <string>         # human-readable, derived from rules

controlPlaneActions:
  - skill: <skill-id>
    plane: control_plane
    autonomyTier: <enum>
    riskTier: <enum>
    actions: [<action-ref>, ...]

projectionPolicy:
  canonicalStateSource: repo-local-ledger | external-system | hybrid
  pathPattern: <string>
  externalSystems:
    - kind: github-issues | jira | linear | ...
      role: collaboration-surface | projection-target | system-of-record
      mutationRequiresApproval: bool

riskPatterns:
  - patternRef: <risk-pattern-id>         # risk pattern catalog
    mitigations: [<mitigation-clause>, ...]
    evidenceRefs: [<case-file-item-ref>, ...]

controlAssessment:                        # OSCAL-shaped subset
  catalogRefs: [<catalog-uuid>, ...]
  controlImplementations:
    - controlId: <oscal-control-id>
      mappingStatus: implemented | partial | planned | not-applicable
      implementedBy:
        skills: [<skill-id>, ...]
        evidence: [<evidence-id>, ...]
      statement: <string>

freshness:
  reviewedAt: <iso-date>
  implementationFingerprint:              # content hash of implementation map
    algorithm: sha256
    value: <hex>
  driftPolicy: <string>

knownGaps:
  - id: <gap-id>
    summary: <string>
    severity: blocking | important | minor
    plannedResolution: <string> | null
```

**Key shape changes from v0.1:**

1. **`allowedActions`/`prohibitedActions` are action-catalog references**, not free-text strings. The catalog ships in `gaps/catalogs/actions/v1.yml` with ~80–150 named primitives covering the action surface (draft, propose, edit-within-boundary, mutate-external, approve-gate, escalate, etc.). Specs may extend with process-local actions declared in `process.localActions[]`.

2. **`evidenceModel.caseFileItems[]` are typed entities with `id`, `kind` (from catalog), `shape`, `producer`, `consumer`**. Every reference elsewhere in the spec uses `<evidence-id>`, enforced.

3. **`stateModel` and `gates[].decision` are executable.** State transitions have guards; gate decisions are DMN-style rule tables. A generator can derive an Input Quality Gate from `evidenceInputs`, a Rules block from `allowedActions`/`prohibitedActions`, and Stop Conditions from transition guards — automatically, with concrete content.

4. **`controlAssessment` is OSCAL-shaped.** `catalogRefs` resolve to OSCAL catalogs in `gaps/catalogs/controls/`. `controlImplementations[].controlId` resolves to a control UUID in those catalogs. Round-trip to OSCAL is mechanical.

5. **`conformanceLevel`** is declared by the author. `descriptive` = a v0.1-style narrative spec lifted to v1 shape. `machine-validatable` = all cross-references resolve, all catalog refs valid. `generative` = additionally the state model and gate decisions are complete enough to drive skill generation.

6. **`implementationFingerprint`** replaces v0.1's `freshness.implementedBy` list. A content hash detects implementation drift mechanically.

## Layer 2: Catalogs

Five catalog files, shipped in `gaps/catalogs/`:

**`actions/v1.yml`** — controlled vocabulary of action primitives. Each entry:
```yaml
- id: draft-artifact
  label: Draft an artifact for review
  category: data-plane | control-plane | meta
  defaultAutonomyTier: draft
  defaultRiskTier: low
  examples:
    - "draft a PRD"
    - "compose a verification report"
  definition: >
    Produce a reviewable artifact without persisting it as approved state.
```
Initial catalog covers the union of the four current reference specs' `allowed`/`prohibited` semantics, normalized to ~80–120 primitives. Process-local extensions allowed via `process.localActions[]` but require justification.

**`evidence-kinds/v1.yml`** — taxonomy of evidence types. Categories: `observation`, `attestation`, `finding`, `decision-record`, `artifact-ref`, `audit-event`, `external-reference`. Each kind declares default shape, default producer, default retention.

**`risk-patterns/v1.yml`** — formalizes the nine governed-autonomy risk patterns from `docs/governed-autonomy/uncontrolled-ai-risk-patterns.md` with stable IDs (`chat-as-control-plane`, `unbounded-delegation`, etc.). Each entry includes signal indicators, default mitigations menu, and example evidence.

**`controls/nist-ai-rmf.json`** — OSCAL catalog file for NIST AI RMF subcategories (Govern / Map / Measure / Manage).
**`controls/iso-42001-annex-a.json`** — OSCAL catalog file for ISO/IEC 42001 Annex A controls.
**`controls/eu-ai-act-articles.json`** — OSCAL catalog file for key EU AI Act articles (Article 9 risk mgmt, Article 14 oversight, Article 26 deployer obligations).

Catalogs are versioned (`catalogVersion: v1`). v2 catalogs introduce additive entries; breaking changes bump GAPS spec major version.

## Layer 3: Validator v1

Replaces `scripts/validate-gaps.py` (kept for v0.1 backwards compat through deprecation window). New checks:

1. **JSON Schema with conditional shapes.** `if/then/else` for `conformanceLevel` gating which sections are required. Strict `additionalProperties: false` except where extension points are declared.

2. **Catalog reference resolution.** Every `actionRef`, `evidenceKindRef`, `riskPatternRef`, OSCAL control UUID resolves to a catalog entry. Process-local extensions are accepted only when declared in `process.localActions[]` / `process.localEvidenceKinds[]`.

3. **Internal cross-reference integrity.** Every `<role-ref>`, `<lane-ref>`, `<state-id>`, `<transition-id>`, `<gate-id>`, `<evidence-id>`, `<skill-id>` resolves. Gate ids unique across spec. State ids unique per lane.

4. **State machine soundness.** Per lane: exactly one `isInitial`, at least one `isTerminal`, every state reachable from initial, no orphan transitions, no dead ends without `isTerminal: true`.

5. **Gate decision completeness.** Either all input combinations covered by rules, or an `else` clause provided. Inputs referenced in `when` expressions must be declared in `decision.inputs`.

6. **Authority/action consistency.** An `allowedAction` and `prohibitedAction` cannot be the same action-id. Decision rights for a role must be a subset of actions the role can perform per the action catalog's role-affinity hints.

7. **Conformance level gating.** `generative` specs require: every lane has a non-empty `stateModel`, every transition has a `guard`, every blocking gate has a `decision`, every evidence input has a typed shape.

8. **OSCAL substrate validity.** `controlAssessment` block re-validated as a subset OSCAL assessment-plan when extracted. Use `oscal-cli` if available; fall back to Python JSON Schema check against bundled OSCAL schemas.

9. **Implementation conformance (when `implementation.yml` present).** Replaces v0.1's substring phrase match with declarative section schemas: each lane → skill binding declares which states/transitions/gates the skill implements, and the validator confirms the skill's generated content (via Layer 4 generator) matches what's in `skills/<skill-id>/SKILL.md`. This is the round-trip check at validate time.

CLI shape: `scripts/validate-gaps.py <spec> [--level descriptive|machine-validatable|generative]`.

## Layer 4: Generator v1

Replaces `scripts/generate-gaps-skill-package.py`. Templates are gone for the load-bearing sections — content is derived from spec structure.

Per lane, the generator emits a `SKILL.md` with:

- **Input Quality Gate** section derived from `evidenceInputs[].shape.required` + `entry_conditions` from the initial state's transition guards
- **Rules** section derived from `authority.allowedActions` (catalog definitions inlined) and `authority.prohibitedActions`
- **State Loop** section new: pseudocode-shaped Markdown table of states + valid transitions
- **Gates** section: per gate, the `decision` table rendered as a Markdown table with `when`/`then` columns
- **Stop Conditions** section derived from terminal states + escalating gate paths
- **Evidence To Produce** section from `evidenceOutputs[].shape`
- **Non-claim language** still inlined as today, but smaller because most content is now spec-derived

Plus:
- `agents/openai.yaml` manifest (mechanical from spec)
- Command adapters in `commands/<process-id>/<command>.md` and `.toml`
- `agent-skills.json` manifest (mechanical)
- `.claude-plugin/plugin.json` and `gemini-extension.json` (mechanical)
- A regenerable `implementation.yml` derived from spec — no longer hand-authored

CLI shape: `scripts/generate-gaps-skill-package.py <spec> [--output-root <dir>] [--mode preview|adopt]`. Preview still writes under `gaps/generated/<process-id>/`.

A "generative" conformance-level spec must produce a skill package that, when fed back through `validate-gaps-implementation.py`, passes without human content authoring. This is the v1 acceptance test.

## Layer 5: Migration + Reference Specs

**Migration tool**: `scripts/migrate-gaps-v0-to-v1.py <v0.1-spec> [--out <v1-spec>]`. Best-effort translation:

- Free-text `allowed`/`prohibited` strings → fuzzy-matched action catalog refs, with unmatched items emitted as `process.localActions[]` candidates + a TODO comment
- Flat `states[]` lists → state model skeleton with `isInitial` guessed from first item, `isTerminal` guessed from terminal-shaped names (`closed`, `done`, `archived`)
- Prose `approvalCondition`/`escalationCondition` → preserved as `decision.rules[].when` expressed in a `prose:` fallback that machine-validatable-level rejects but descriptive-level accepts
- v0.1 `controlMappings` → OSCAL `controlAssessment` skeleton with `mappingStatus: unmapped` preserved as `planned`

Migration output is always `conformanceLevel: descriptive` — humans uplift to `machine-validatable` then `generative` deliberately.

**Reference spec ports**: the four existing reference specs (`gadd`, `compliance-review`, `incident-response`, `procurement-approval`) ported to v1. At least one (recommend `compliance-review`) brought to full `generative` conformance to prove the round-trip claim. `gadd` is the highest-value port because `reference-packages/gadd/` ties to it; reaching `generative` for `gadd` proves the format can drive a real published skill suite.

**One new reference spec** added: a casework process that stresses the CMMN-conceptual state model more than any current spec (e.g., a benefits-eligibility review with adaptive state, time-limit milestones, and multi-authority escalation). This catches modeling gaps before v1.0.0 ships.

## Layer 6: Round-trip + Reverse-lift + Docs

**Round-trip command**: `scripts/gaps-round-trip.py <spec>` runs `generate → validate-implementation → lift → diff`. Diff is structural (semantic equivalence), not textual. Passing round-trip is the `generative`-level conformance gate.

**Reverse lift**: `scripts/gaps-lift.py <skill-package-root>` produces a v1 spec draft from a skill package. Used for: (a) round-trip diffing, (b) lifting an existing handwritten skill suite (like the gadd reference package) into a spec when one doesn't exist yet, (c) regression detection when skills are hand-edited.

**Docs**: a new `docs/governed-autonomy/gaps/` section with:
- `README.md` — what v1 is, what changed, conformance levels
- `format.md` — the spec format reference
- `catalogs.md` — how to read and extend the catalogs
- `substrates.md` — the OSCAL/CMMN/DMN adoption rationale and what's adopted vs. aligned
- `authoring-guide.md` — for LLM and human spec authors; uses catalog-driven worked examples
- `generator.md` — what the generator emits and why
- `migration-from-v0-1.md` — step-by-step
- `round-trip.md` — the round-trip discipline
- Updates to existing `docs/governed-autonomy/case-study-gadd.md` to reference v1

Skills: `skills/gaps-author`, `skills/gaps-validate`, `skills/gaps-generate` rewritten to drive the v1 tooling, with `skills/gaps-lift` and `skills/gaps-round-trip` added.

## Verification

End-to-end acceptance tests for v1.0.0 release:

1. **Catalogs lint clean**: `python3 scripts/validate-catalogs.py gaps/catalogs/` exits 0. Validates internal references, OSCAL catalog conformance, action category coverage.

2. **All v1 reference specs validate at declared conformance level**: `python3 scripts/validate-gaps-v1.py gaps/examples/<process-id>/ga-process.v1.yml --level <declared>` exits 0 for each of the four ports plus the new casework spec.

3. **Round-trip passes for the generative reference spec**: `python3 scripts/gaps-round-trip.py gaps/examples/compliance-review/ga-process.v1.yml` exits 0 with empty structural diff.

4. **Generated skill package validates without manual content authoring**: For the generative-level spec, `generate → validate-gaps-implementation-v1` passes with zero human edits between steps.

5. **Migration produces valid descriptive-level v1 specs**: For each v0.1 spec, `migrate-gaps-v0-to-v1.py` produces a file that validates at `descriptive` level.

6. **Reverse lift recovers structural equivalence**: For the generative spec, `gaps-lift.py reference-packages/<process-id>` produces a spec that round-trips with empty diff against the source.

7. **Existing suite still passes**: `./scripts/validate-governed-autonomy.sh` exits 0; v0.1 reference specs still validate against v0.1 validator (deprecation window).

8. **Documentation linkcheck**: All `docs/governed-autonomy/gaps/*.md` internal links resolve; embedded YAML examples validate.

## Phased Implementation Order

This design is the v1.0.0 architecture. Each layer becomes its own implementation plan via the writing-plans skill. Recommended order:

1. **Layer 1 + Layer 2 together** — formal model (v1 schema) and catalogs (actions, evidence kinds, risk patterns, OSCAL control catalogs). These are co-dependent; the schema references catalog shapes and the catalogs validate against the schema's reference points. One implementation plan.

2. **Layer 3** — validator v1. Standalone implementation plan. Lands with the v1 schema; unlocks every downstream layer.

3. **Layer 5 migration tool + reference spec ports** — migrator first, then port the four v0.1 specs to v1 (initially at `descriptive` conformance). One implementation plan.

4. **Layer 4** — generator v1. Standalone implementation plan. Brings `compliance-review` (or chosen pilot) to `generative` conformance and demonstrates round-trip.

5. **Layer 6 round-trip + lift + docs** — final polish. Standalone plan. Brings remaining reference specs to `machine-validatable` minimum; one to `generative`; ships docs.

6. **Release** — bump to v1.0.0, deprecation notice on v0.1 tooling, announce in `README.md`.

Each phase ends with a passing subset of the verification list above. v1.0.0 is released only when all eight verification items pass.

## Out of Scope for v1.0.0

- Executable runtime for state models (GAPS specs remain declarative; skills execute, not the spec itself)
- BPMN export (deferred; OSCAL export sufficient for v1 interop story)
- Web UI for spec authoring (CLI + LLM-driven authoring only)
- Cross-spec process composition (each spec is one process)
- Versioning across multiple v1.x catalogs in a single repo (one catalog version per repo at a time in v1)
- Standards adoption beyond OSCAL/CMMN-concept/DMN-concept (no SOC 2, no ITIL, no ArchiMate in v1)
